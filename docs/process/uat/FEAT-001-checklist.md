## 二、验收项（`U-NN`）

### U-01 首页八件商品

- **判定判据**：列表展示八件商品（`AC-01`）· 列表名称有序（`AC-03`）
- **具体怎么试**：浏览器打开 `http://127.0.0.1:3000/`，看首页商品列表；**刷新一次**再看。
- **期望观察**：恰好 **8 件**商品；每件都有商品名称与价格；两次刷新后**顺序一模一样**，没有商品忽多忽少。

### U-02 界面能看懂（观感 · 交人裁）

- **判定判据**：前端同端口可达（`AC-27`）—— 仅结构性判据；**观感部分不作判据**
- **具体怎么试**：在首页、详情页、购物车页各停留 10 秒，只回答两个问题：① 能不能一眼看出「这是什么、我现在该点哪」；② 有没有文字被裁掉、挡住或看不清。
- **期望观察**：页面能正常显示（不白屏、无脚本报错弹窗）；至于「顺不顺眼」**只记录原话与截图，不判通过与否**（`RSK-04`：主观质量交人裁）。

### U-03 商品字段齐全

- **判定判据**：列表字段齐全（`AC-02`）· 库存字段可见（`AC-05`）
- **具体怎么试**：`curl http://127.0.0.1:3000/api/v1/products` 看返回；再对任意一件商品看它的字段。
- **期望观察**：每件商品都有**商品名称、描述、价格（分）、库存**四项且都不是空；描述不是空字符串；库存是正整数。

### U-04 详情与列表一致

- **判定判据**：详情与列表一致（`AC-06`）· 详情价与总额相符（`AC-07`）
- **具体怎么试**：在首页记住某件商品的**名称与价格**（如《手冲咖啡壶》），点它的名称进详情页；回列表再对一遍。
- **期望观察**：详情页的名称、价格、库存与列表上**完全一样**，没有「列表一个价、详情另一个价」。
- **不依赖主键**：进详情靠**点商品名**，不去看 URL 里的编号，也不在判据里写编号。

### U-05 首访下发购物车

- **判定判据**：首访下发购物车（`AC-08`）
- **具体怎么试**：换一个**全新无痕窗口**打开 `http://127.0.0.1:3000/`，直接进购物车页（先不加任何商品）。有 curl 的话：`curl -i http://127.0.0.1:3000/api/v1/cart`。
- **期望观察**：购物车是**空的**（不报错、不要求登录）；响应头里有 `cartId` cookie（`HttpOnly`）；页面显示空车提示而不是空白或报错。

### U-06 加入购物车

- **判定判据**：加购单件成功（`AC-10`）· 购物车结构完整（`AC-09`）
- **具体怎么试**：在任意商品下点「加入购物车」，然后进购物车页。
- **期望观察**：该商品出现**一行**、件数 **1**；行小计 = 单价 × 1；页面顶部件数徽标随之变化；总额 = 各行小计之和。

### U-07 重复加购累加

- **判定判据**：重复加购累加（`AC-11`）
- **具体怎么试**：对**同一件**商品再点两次「加入购物车」。
- **期望观察**：**仍然只有一行**（没有出现两行同名商品）；件数从 1 变 3；行小计与总额同步变大。

### U-08 非法件数被拒

- **判定判据**：非整数件数拒绝（`AC-12`）· 载荷与类型非法（`E-11`，部分）
- **具体怎么试**：用 HTTP 直连（curl）对已在车里的商品发：`POST /api/v1/cart/items`，body 为 `{"productId":"<该商品的 id>","quantity":1.5}`；再发一次 `"quantity":"2"`（带引号的字符串）。
- **期望观察**：两次都返回 **400**，响应体里有 `code` 与中文 `message`；随后查购物车，**行数与件数完全没变**（没有半件、没有多一行）。
- **说明**：`productId` 从 `GET /api/v1/products` 按**商品名称**解析得到 —— 这是唯一的例外（路径参数需要 id），**判据本身仍按名称描述**。

### U-09 件数上下限

- **判定判据**：件数上下限拒绝（`AC-13`）
- **具体怎么试**：在购物车页把该行件数依次改成 **1**、**8**、**9**、**0**；HTTP 侧再用 `POST` 试 `quantity` = `-1`。
- **期望观察**：**1 和 8 允许**（改得动）；**9、0、-1 被拒**并在界面上给出可读提示，**数字保持不变**（不会变成 9 也不会清零）。

### U-10 单品上限

- **判定判据**：单品上限拒绝（`AC-14`）
- **具体怎么试**：该行已在 8 件时，再点「加一件」（或再发一次 `quantity:1`）。
- **期望观察**：被拒并提示已达上限；该行**仍是 8 件**；总额不变。

### U-11 无货商品被拒

- **判定判据**：加购无货拒绝（`AC-15`）· 库存临界清零（`E-07`）
- **具体怎么试**：先把某商品买到**库存为 0**（见 U-14 的做法）；然后回商品页点它的「加入购物车」；再查购物车。
- **期望观察**：加购被拒（提示缺货 / 无货）；购物车**没有多出这一行**、总额不变。（若客户端直接调接口，状态码为 **409** 且 `code` 与「缺货」相关。）

### U-12 行数上限

- **判定判据**：购物车行数上限（`AC-16`）· 行数上限退化（`E-02`）
- **具体怎么试**：往购物车加**不同的**商品，一直加到装不下为止。
- **期望观察**：能放下 **8 种不同商品**；加第 **9 种**时被拒并提示最多放 8 种；车里**仍是 8 行**。
- **注意（Gate4 前口径改判，登记性）**：若本次种子里只有 8 件商品，这条**天然压不到**（8 件商品最多就 8 行）—— 这是**本包的设计后果，不是「漏验」**。本条的**判据与步骤保持不变**（上面的步骤/期望照旧执行并如实记录读数），但**结论口径**由「未覆盖」改为 **「不由 UAT 承载（自动化专有面）」**：默认种子恰 8 条 ⇒ 第 9 行**只能在注入 ≥9 条种子的自动化面构造**（`createApp({ seed })`），与 **`E-14`（种子字段非法）同类处置** —— 界面与 HTTP 均无种子注入入口。**不得写成「不通过」，也不得自己造数据 / 改种子文件**；正确写法是「UAT 面不可达，已由自动化面 `TC-FEAT-001-16` / `TC-FEAT-001-E02` 覆盖」。**第 1、2 轮实读**：默认 8 条全加购后恰 8 行（上限压满）；试一个不存在的编号 → `404 NOT_FOUND`（那是 `E-04` 的面，**不是**行数上限面）。证据：`reports/uat/evidence/r2-U-12-未覆盖确认-01-原始响应.txt`（第 1 轮存档见 `reports/uat/FEAT-001-uat-1.md` §2 `U-12`）。

### U-13 改件数与删行

- **判定判据**：购物车改与删（`AC-17`）
- **具体怎么试**：购物车里放 **2 件不同商品**（件数分别 1 和 2）；把第一行改成 **3**；再把第二行删掉。
- **期望观察**：改完第一行小计 = 单价 × 3、总额变大；删完只剩 **1 行**、**那件被删的商品找不到了**、总额 = 剩余行的小计。

### U-14 下单即已支付

- **判定判据**：下单即支付成功（`AC-18`）· 下单扣减库存（`AC-19`）· 订单号唯一（`AC-25`）· 空车下单拒绝（`AC-22`）
- **具体怎么试**：① **先空车去结算页**（购物车点「去结算」）**并点一次「提交订单」**；② 再加 1 件商品，记下这件商品**当前库存**，点「去结算」→ 在**结算页**点「提交订单」；③ 回商品页看这件商品的库存。
- **期望观察**：① 空车被拒并提示购物车是空的，**没有产生订单**；② 下单成功、显示**订单号**、订单状态是**已支付**；③ 库存**正好少了买走的件数**（不是少 1 就是少 1，买 2 就少 2）。

### U-15 缺货下单被拒

- **判定判据**：缺货下单拒绝（`AC-20`）· 刷新即重置（`AC-30`）
- **具体怎么试**：选一件商品，把购物车里的件数加到**明显超过它的库存**（例如库存 2、车里 8）；点「去结算」→ 在**结算页**点「提交订单」；再看商品库存与订单列表。
- **期望观察**：下单被拒并提示**库存不足**；商品库存**一点没变**；订单列表**没有多出这一单**；购物车**没被清空**（东西还在，可以改小再试）。

### U-16 下单后清空车

- **判定判据**：下单后清空车（`AC-23`）· 重复提交下单（`E-10`）
- **具体怎么试**：成功下单一笔后，回购物车页 -> 再进结算页、立刻**再点一次**「提交订单」；然后回购物车页刷新。
- **期望观察**：第二次被拒（提示购物车是空的），订单列表**只多了一单**；购物车页刷新后是**空的**。

### U-17 订单列表

- **判定判据**：订单列表可读（`AC-24`）· 订单列表同端口（`AC-26`）· 统一错误响应（`AC-29`）
- **具体怎么试**：连下 **2 笔**订单（可以先加 1 件、下单，再加 1 件、下单），打开订单列表页。
- **期望观察**：**2 条**订单；**后下的那笔在最上面**；每条都有订单号、状态（已支付）、件数、总额（元，两位小数）。
- **顺带一查（`AC-29`）**：访问一个不存在的商品页（随便改一个 URL 里的商品编号），应看到**可读的中文提示**而不是空白页或一堆英文报错堆栈。

### U-18 换窗口就换人

- **判定判据**：刷新即重置（`AC-30`）· 跨客户端隔离（`E-09`）
- **具体怎么试**：在无痕窗口 A 里放好购物车并下过单；另开一个**全新的**无痕窗口 B（或另一个浏览器 / 另一个 curl cookie 文件），看购物车与订单列表。
- **期望观察**：B 的购物车是**空的**、订单列表是**空的**，看不到 A 的东西；A 回头看自己的购物车与订单**仍在**。

### U-19 全程不用界面也能走通

- **判定判据**：无界面直连可用（`E-12`）· 畸形 cartId（`E-06`）· 未知统计字段不泄露（`E-13`）· 不存在商品详情（`E-03`）· 不存在商品加购（`E-04`）· 改删不存在行（`E-05`）· 载荷与类型非法（`E-11`）
- **具体怎么试**：只用 curl（维护 cookie jar）走一遍完整链路：列表 → 按名称解析出商品 id → 详情 → 加购 → 改件数 → 删行 → 下单 → 订单列表。另外：① 把 cookie 里的 `cartId` 改成乱码再请求购物车；② 请求一个不存在的商品编号；③ 对车里不存在的商品发删除；④ 发一个坏 JSON（如 `{`）。
- **期望观察**：① 全链路**每一步都可达**（没有「只有点界面才能触发」的动作）；② 乱码 cookie ⇒ 不报 5xx，给一辆**新的空车**；③ 不存在的商品 ⇒ **404** 且提示「找不到」；④ 删不存在的行 ⇒ **404**；⑤ 坏 JSON ⇒ **400**；所有错误响应都是**同一种形状**（`code` + 中文 `message`），**没有**英文堆栈、没有文件路径。

## 四、人工边界项（需 curl / 并发 / 真机驱动，界面点不出来或需时序观察）

### U-20 金额整数无尾差

- **判定判据**：总额分为单位（`AC-21`）· 详情价与总额相符（`AC-07`）
- **具体怎么试**：挑**两件不同商品**各加进车（件数分别 1 与 2），记下它们的**分价** `P1` `P2`；下单后用 curl 看订单 JSON 的 `totalCents`（或对比购物车页显示的元价与手算结果）。
- **期望观察**：订单总额 = `P1×1 + P2×2`（**按分**算，结果必须是整数）；页面上的元价 = 分 ÷ 100 且**两位小数**；**没有** `xx.999999` 或 `xx.000001` 这类尾差；订单 JSON 里**不出现以元为单位的金额字段**。

### U-21 并发抢最后一件

- **判定判据**：并发抢最后一件（`E-08`）
- **具体怎么试**：把某件商品买到**只剩 1 件**；用**两个不同客户端**（两个 curl cookie 文件，或一个浏览器 + 一个 curl）**同时**（背靠背、尽量同一时刻）各下单这件商品 1 件。
- **期望观察**：**恰好 1 单成功**（201），另 1 单被拒（409 + 库存不足）；之后该商品库存 **恰好 0**（**绝不能是负数**）；成功订单数 = 1。
- **注意**：这条是**人工并发**，不保证每次都能撞上；若两次请求有明显时间差（第 1 单已成功且库存归零），则本次**不构成并发证据** ⇒ 如实记为「未覆盖并发」而非「通过」。

### U-22 默认种子与字段

- **判定判据**：种子商品可读（`AC-28`）· 列表只读不可改（`AC-04`）· 默认种子八条（`E-01`）
- **具体怎么试**：① curl 拉一次列表，数条数并检查每件的名称 / 分价 / 库存类型；② 对 `/api/v1/products` 发 `POST` / `PUT` / `DELETE`（不带 body 也行），再拉一次列表对比；③ 隔一会儿（或重启服务前后）再拉一次。
- **期望观察**：① **默认恰为 8 条**商品，名称非空、分价是正整数、库存是**正整数**；② 三个写方法**都没能改动**商品数据（列表前后**逐件完全一样**）；③ 重启服务后商品数据**回到初值**（库存也回到初值）。
- **说明（`E-01` 口径已随 `prdVersion` 2 修正）**：**「注入 7 条 / 9 条种子能否启动」不再是判据** —— 注入路径**接受任意条数**（这正是 `AC-16` 外点得以构造的前提）；而「注入**字段非法**的种子会抛错」（`种子字段非法 E-14`）**只有注入路径能构造**。两者都属自动化测试的面 ⇒ uat 只需记录「未以界面覆盖该边界」，**不得**自行改种子文件、**不得**把它写成「不通过」。

### U-23 首帧与提交中的可观察态（真机 · 无 PRD 判据锚点）

- **判定判据**：**本条不挂任何 PRD `AC` / `E` 编号** —— 它观察的是 **UI 规格** `UI-27`（首帧「加载中…」占位）与 `UI-28`（「提交中…」按钮禁用态），这两条**没有对应的 PRD `AC` / `E` 锚点**，故**不在自动化断言面**（判据号只能挂 `TC-FEAT-001-<AC/E>`，test 不得擅自新增判据）。**这是观察面登记，不是新增产品判据**。
- **具体怎么试**（用真浏览器，建议 CDP 驱动无头 Edge；纯手点也可）：
  ① 打开首页 / 商品详情 / 订单列表，**观察首帧**：数据到达前页面是否出现「**加载中…**」占位（可在网络面板限速或看首屏快照）；
  ② 在结算页点「提交订单」，**在响应返回前**看按钮**是否变为禁用 + 文案「提交中…」**；
  ③ 在 ② 的同一时刻**再点一次**「提交订单」，然后在服务端 / 网络面板**数实际发出的下单请求条数**。
- **期望观察**：① 首帧出现**可读的「加载中…」占位**（不是白屏、不是无反馈的静止页）；② 提交期间按钮**被禁用**且文案变为「**提交中…**」；③ 连点**只产生 1 次**下单请求（不产生第二次网络请求 / 不出现第二张订单）。
- **注意**：③ 与 `E-10`（重复提交 ⇒ 第 2 次 `409 CART_EMPTY`）**不是同一件事** —— `E-10` 是**服务端**对第二次**已发出**的请求的处置（自动化面）；本条的 ③ 是**前端是否压根没发第二次请求**（体验面）。两者都通过才算好；只过 `E-10` 不代表前端防重做对了。
- **证据要求**：截图或 CDP 抓取的网络请求清单，落 `reports/uat/evidence/`。若因装置限制（如拿不到首帧快照）覆盖不了 ①，**如实记为「未覆盖」并写明装置限制**，不得与「通过」混列。
- **来源登记**：`UI-27` / `UI-28` 来自 UI 规格（ui-designer 交付），**无 PRD `AC` / `E` 锚点** ⇒ 由本条在 UAT 面承接；ui-designer 已把 §一 注记中「这三条由 test 断言」收敛为只留 `UI-03`。

### U-24 件数上限禁用态（真机 · `UI-11`，UAT 承载）

- **判定判据**：**本条不挂任何 PRD `AC` / `E` 编号** —— 它观察的是 **UI 规格** `UI-11`（件数已达 8 时该行「＋」处于**禁用**、点击**不产生任何请求**、件数保持 8；件数为 1 时「－」同理禁用）。UI 规格 §一 已把它从自动化面**改判为 UAT 承载**（**jsdom 不执行 `<script type="module">`** ⇒ 静态 DOM 里没有这些节点、也拿不到点击后的网络行为）⇒ 只能真机看。**这是观察面登记，不是新增产品判据**（`AC-13`/`AC-14` 只说「上限 8」这条规则，**不描述「禁用态」这一 UI 承载**）。
- **具体怎么试**：真浏览器里加购一件商品 → 在购物车页把该行件数点到 **8**（用「＋」）→ ① 看「＋」的 `disabled` 状态；② 在**这个已禁用的「＋」上真实点击**一次，同时抓网络请求；③ 把件数减到 **1**，看「－」是否同样禁用；④ 连续点「＋」看是否出现 4xx 提示。
- **期望观察**：① 件数 **8** 时该行「＋」**禁用**（`disabled=true`）；② 点击**不产生任何请求**（网络面板 0 条）、件数**仍为 8**、**不出现**新的 4xx 提示；③ 件数 **1** 时「－」同样禁用；④ **无新增可见文案** —— 上限以**禁用态**表达，不占用任何契约错误码。
  与之**不同的一条**：库存 **< 8** 时「＋」**不**禁用、点一次弹一次缺货提示（UAT `V-01`，**行为与契约一致**、登记为待裁定 `Q-9`）—— 两者**不要混判**。
- **证据要求**：截图（禁用态）+ 网络请求清单（证明 0 请求），落 `reports/uat/evidence/`。
- **第 1、2 轮实读（两轮均通过）**：`disabled=true`、真实点击**请求 0 条**、件数仍 8、无新提示。证据：`reports/uat/evidence/U-11-件数上限禁用态-01-八件时加号禁用.png`、`r2-UI-11-件数上限禁用态-01.png`、`uat-browser-readings.txt` / `r2-uat-browser-readings.txt`。
- **来源登记**：`UI-11` 来自 UI 规格（ui-designer 交付），**无 PRD `AC` / `E` 锚点** ⇒ 由本条在 UAT 面承接；UI 规格 §一 注记的三条 UAT 承载项（`UI-11` / `UI-27` / `UI-28`）在本清单中对应 **`U-24`（`UI-11`）** 与 **`U-23`（`UI-27` + `UI-28`）**，**两处口径已对齐**。
