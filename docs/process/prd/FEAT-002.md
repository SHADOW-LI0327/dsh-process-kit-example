## 4. 验收标准（`AC-N`，Given / When / Then）

> **标题格式（强制）**：`### AC-N <中文短名（6–12 字）>｜<一句话结论>`。短名取材于结论句主干、**一处定死**，下游（台账 / 契约 / UAT 清单 / 测试 / 报告 / 证据文件名）一律照抄，禁止另起别名。
> 每条 `AC` 齐备**可验证性四要素**：**判定粒度** · **数值口径** · **平台差异声明** · **对应测试用例编号**（另附**依据**与**边界四要素**，后者仅阈值 / 上限类适用）。
> **判据不得依赖夹具主键**：一律用「商品名称 + 可观察行为」定位；`orderNo` 只作**响应间比较**用，不得写死在判据里。
> **暂定值标记**：凡依据 `Q-10` 最小可用假设（商品 ≤1 千 / 日单 ≤1 万 / 并发 ≤50）推导的阈值 / 上限，一律标注 **「暂定值（依据 `Q-10` 最小可用假设）」**；其余暂定值标注其来源裁定。

### 4.1 持久化与事务（`R-01`）

### AC-01 重启数据仍在｜进程重启后购物车、订单与库存仍保持重启前状态

- **Given** 客户端 A 已注册登录、加购并成功下单一次；重启前记录其订单条数 `M`、购物车 `items` 与某商品库存 `S`
- **When** 停掉进程并以**同一库文件**重启，客户端 A 重新 `GET /api/v1/orders`、`GET /api/v1/cart` 与 `GET /api/v1/products/{id}`
- **Then** 订单条数**仍为 `M`**、订单号仍可按 `orderNo` 命中；购物车 `items` 与重启前**逐项相等**；该商品 `stock === S`（**不得**回到种子初值）。**取代 `FEAT-001 AC-30` ②**：本条期望与「重建后库存回到种子初值」相反
- **可验证性要素**：**判定粒度** = 按「单」与「件」（整数计数，不涉时间窗）；**数值口径** = `M` / `S` 为**实测值**（重启前后各读一次），种子条数 8 与库存初值 8 为**暂定值**（沿用 `FEAT-001 Q-1` 暂定值，可一句话改）；**平台差异** = 桌面 / 单测与真机**一致**（同一 Node 运行时 + 同一库文件；差异仅在于真机是进程级重启、单测是**重建实例指向同一临时库文件**，二者对「数据是否落盘」的判定等价）；**边界四要素** = 不适用（无阈值，是集合与取值的等值断言，按总纲 §6.4 第 24 条比集合成员与行数）
- **依据**：`R-01` + 核对件 `§2.1` 展开①「数据在进程重启后仍在」+ `§4.2 S-1` + `Q-3`（身份载体）
- **前置设计约束（必须写死，否则本条不可构造）**：**会话必须持久化** —— `sessions` 落库、重启后**旧 cookie 仍有效**（直到绝对 / 空闲过期，字面值见契约 §四）。若会话只存内存，重启后 A 的请求会返回 `401`，本条会被误判为「持久化没做」。会话载体口径**二选一并已定：选「持久化」**（另一选法是「重启后重新登录再比对」，本包**不采用**，以免同一行为被测试与 UAT 各判一套）
- **对应测试用例**：`TC-FEAT-002-01`

### AC-02 隔离语义保留｜换新会话看不到他人购物车与订单，重启后仍按归属隔离

- **Given** 账号 A 已有购物车与订单；客户端 B 为**全新会话**（无 cookie）
- **When** ① B `GET /api/v1/cart` 与 `GET /api/v1/orders`；② 重启进程后 B 再次请求二者，并用 B 的购物车 cookie 请求 A 的订单详情
- **Then** ① B 的 `items` 为**空数组**、订单面按未登录处置（`401 UNAUTHENTICATED`，`AC-14`）；② 重启后仍为空 / 仍 `401`；B 拿不到 A 的任何 `orderNo` 或购物车行（**保留 `FEAT-001 AC-30` ① 的隔离语义**）
- **可验证性要素**：**判定粒度** = 按「件」与「单」（比集合成员与行数，差异必须为空）；**数值口径** = 空集合为**实测值**；**平台差异** = 一致（cookie 由 HTTP 层处理，测试用显式 cookie jar，不依赖浏览器存储）；**边界四要素** = 不适用（无阈值）
- **依据**：核对件 `§4.2 S-1`（「① 必须保留 —— 别把隔离一起删了」）+ `Q-3` 子项 3-a④
- **对应测试用例**：`TC-FEAT-002-02`

### AC-03 下单事务原子｜下单的建单、扣库存、清车三步要么全成要么全不成

- **Given** 已登录账号，购物车含两件不同商品，其中**后一件的所需件数大于其当前库存**（构造 `INSUFFICIENT_STOCK`）；下单前后各记：订单条数 `M`、两件商品库存 `S1` `S2`、购物车 `items` 长度 `L`
- **When** `POST /api/v1/orders`
- **Then** HTTP `409` + `code === "INSUFFICIENT_STOCK"`；**订单条数仍为 `M`**、**`S1` 与 `S2` 均未变**、**购物车 `items` 长度仍为 `L` 且行内容逐项相等**（不得出现「扣了第一件但没建单」或「建了单但没扣库存」的部分写入）
- **可验证性要素**：**判定粒度** = 按「单 / 件 / 分」（整数与集合成员）；**数值口径** = 实测值（下单前后各读一次）；**平台差异** = 一致（同一库文件 + 单进程；`DatabaseSync` 同步 API 使事务与请求处理在同一线程内完成，无跨线程交错）；**边界四要素** = 不适用（原子性断言，非阈值）；**可分辨性** = 判据是「三处前后差异全为空」的确定性等式 + 负向对照（单测须另构造一条**故意删除回滚**的变异实现使其变红，证明本判据可失败，总纲 §6.4 第 29 条）
- **依据**：`R-01` + `Q-8` + 核对件 `§2.1` 展开①「写入具备事务性（下单 = 建单 + 扣库存 + 清车）」
- **对应测试用例**：`TC-FEAT-002-03`

### AC-04 并发下单不超卖｜并发抢购同一库存时成功单数不超过库存且库存不为负

- **Given** 某商品库存 `S`（两档构造：`S = 1` 与 `S = 8`，后者为**暂定种子值**）；`S + 1` 个**互不相同**的已登录账号各持有该商品 `quantity = 1` 的购物车
- **When** 以 `Promise.all` 同时发起 `S + 1` 次 `POST /api/v1/orders`
- **Then** 成功（`201`）恰好 **`S`** 单；其余 `409` + `code === "INSUFFICIENT_STOCK"`；`GET /api/v1/products/{id}` 的 `stock === 0` 且**不得为负**；订单总条数净增恰好 `S`
- **可验证性要素**：**判定粒度** = 按「单 / 件」（整数计数）；**数值口径** = `S` 为**实测值 + 暂定值**（`S = 8` 为沿用 `FEAT-001 Q-1` 的暂定种子库存）；**平台差异** = **桌面 / 单测与真机一致，但有一处必须显式声明**：单进程 + 同步 API 下并发请求由事件循环串行处理，因此「并发」在单测里等价于「同 tick 连续发起」；跨进程并发**不在本包承诺内**（`Q-8` 裁定单实例）。用例必须同时做**同毫秒连续发起**与**多账号交叉**两种构造；**边界四要素**（按库存 `S`）—— **内点** `S - 1` 并发（全部成功）· **外点** `S + 1` 并发（恰好 1 单被拒）· **两端点** `S` 并发（全部成功、库存恰为 0）· **端点外一单位** `S + 1` 并发；**可分辨性** = 最小样本量 = `S + 1` 次请求（离散计数，1 次差异即可判定）
- **依据**：`R-01` + `Q-8` + 核对件 `§3.3` 库存并发缺口 + `RSK-06`（超卖即数据损坏）
- **对应测试用例**：`TC-FEAT-002-04`

### AC-05 落盘库可搬走｜数据落在磁盘库文件，复制文件到新实例可读到同一份数据

- **Given** 服务以 `DB_PATH` 指向的**磁盘库文件**运行，且已产生 1 个账号、1 条订单；记录 `orderNo`
- **When** 停进程 → 把库文件（含 WAL 相关文件）复制到另一目录 → 以新路径启动新实例 → 用同一账号登录并 `GET /api/v1/orders`
- **Then** 两个实例读到**同一条订单**（`orderNo` 命中、`totalCents` 相等）；库文件在磁盘上**真实存在且非零字节**；`AC-07` 保证该路径不落生产库
- **可验证性要素**：**判定粒度** = 按「文件（存在与非零）」+ 按「单」（`orderNo` 等值）；**数值口径** = 文件大小为**实测值**（不设阈值）；**平台差异** = 桌面 / 单测与真机**一致**（`node:fs` 与库文件行为同源）；**唯一差异** = WAL 模式下拷库需带上 `-wal` / `-shm` 或先做检查点 ⇒ **用契约 §七 的备份口径（模块级 `backup()` 或 `VACUUM INTO`）取一致快照**，不用裸 `cp`；**边界四要素** = 不适用
- **依据**：`R-01` + `Q-1` + 核对件 `§2.1` 展开①「数据落在磁盘文件（可备份 / 可搬走）」
- **对应测试用例**：`TC-FEAT-002-05`

### AC-06 迁移播种幂等｜启动期迁移可重复执行、种子播种幂等且不重复插入

- **Given** 一个**空目录**下的新库路径
- **When** ① 启动实例（迁移 + 播种）→ 记录商品条数 `N1`；② 关停后**再启动两次**，每次记录条数；③ 读取库内 schema 版本号
- **Then** 三次启动后商品条数**均为 `N1`**（等于种子条数，默认 8）；schema 版本号**单调不降且最终等于代码内最新版本**；每次启动**不抛错**、不产生重复商品行（按 `name` 定位到的商品**唯一**）
- **可验证性要素**：**判定粒度** = 按「件」（条数）+ schema 版本号（整数）；**数值口径** = `N1` 为**实测值**（对比三次读数）；种子条数 8 为**暂定值**（`FEAT-001 Q-1` 同源）；**平台差异** = 一致（同一库文件 + 同步 API；启动是串行动作）；**边界四要素** = 迁移版本号档：**内点** = 已是最新版本时再次启动（no-op 且不抛错）· **下端点** = 版本 0（空库，首次迁移）· **上端点外** = 库中版本号**高于**代码最新版本 ⇒ **拒绝启动并非零退出**（不得静默降级），该档归 `E-18`；**可分辨性** = 三次重复执行即最小重复次数（幂等判据本身要求 ≥2 次重复）
- **依据**：`R-01` + 核对件 `§2.1` 展开③ `P-12` `P-13` + `AC-07`
- **对应测试用例**：`TC-FEAT-002-06`

### AC-07 注入缝与内存模式｜`createApp` 可注入独立内存或临时库且绝不触碰生产库文件

- **Given** 测试进程与一个**生产库路径**（环境变量已指向它）；调用 `createApp({ seed, store })` 与 `createApp({ dbPath: ':memory:' })` 两种形态

### AC-08 商品分页可选｜商品列表支持可选分页，默认页内返回，越量程被拒

- **Given** 默认种子（8 件）与一份**注入的 1 000 件种子**（暂定值，依据 `Q-10` 最小可用假设「商品 ≤1 千」）
- **When** ① `GET /api/v1/products`（不带参数）；② `?limit=1`、`?limit=200`、`?limit=201`、`?limit=0`、`?limit=-1`、`?offset=-1`；③ 注入 1 000 件后 `?limit=200&offset=800`
- **Then** ① 返回条数 = `min(种子条数, 默认上限)`（8 件种子 ⇒ **恰好 8**，**保持 `FEAT-001 AC-01` 语义不变**）；② `limit=1` 与 `limit=200` → `200` 且条数分别为 1 与 `min(种子数, 200)`；`limit=0` / `limit=-1` / `limit=201` / `offset=-1` → `400` + `code === "INVALID_PAGINATION"`；③ `offset=800` → 返回 **200** 条且首件为第 801 件（按种子顺序）
- **可验证性要素**：**判定粒度** = 按「件」（整数条数）；**数值口径** = 默认上限 **200** 与上限 **200** 均为 **暂定值（依据 `Q-10` 最小可用假设：商品 ≤1 千 ⇒ 默认页 ≈ 1/5 量级）**；1 000 件注入种子为**暂定值**；**平台差异** = 一致（纯整数与 JSON）；**边界四要素**（按 `limit`，闭区间 `[1, 200]`）—— **内点** `50`（通过）· **外点** `0`（拒绝）· **两端点** `1` 与 `200`（通过）· **两端外各一单位** `-1` 与 `201`（拒绝）；`offset` 下界 `0` 通过、`-1` 拒绝（`E-09`）；**可分辨性** = 确定性等式，无统计量
- **依据**：`R-04` + `Q-10` + 核对件 `§3.3` 缺口表「商品列表：需分页 / 筛选（投产量级下必补）」（**筛选**部分归 `§6 N-3` 不做）
- **对应测试用例**：`TC-FEAT-002-08`

### AC-09 订单分页倒序｜订单列表按创建时间倒序分页，默认页内返回，越量程被拒

- **Given** 已登录账号 A 连续成功下单 25 次（订单号两两不同）；账号 B 下单 3 次
- **When** ① A `GET /api/v1/orders`；② A `?limit=1`；③ A `?limit=100`；④ A `?limit=101`；⑤ A `?offset=20&limit=5`；⑥ B `GET /api/v1/orders`
- **Then** ① 返回条数 = `min(25, 默认上限)` 且 `data[0]` 为**最晚创建**的一单（时间倒序）；② 条数 1；③ 条数 = `min(25, 100)`；④ `400` + `INVALID_PAGINATION`；⑤ 条数 5 且不含前 20 条；⑥ 只返回 B 自己的 3 单（`AC-17`）—— **`FEAT-001 AC-24` 的「条数 = 2」语义在 ≤ 默认上限时不变**
- **可验证性要素**：**判定粒度** = 按「单」（整数条数）+ 顺序按**两单的相对先后**（不断言时间戳精度，同刻须有稳定次序）；**数值口径** = 默认上限 **20**、上限 **100** 均为 **暂定值（依据 `Q-10` 最小可用假设：日单 ≤1 万 ⇒ 分页必补；并发 ≤50）**；**平台差异** = 一致；**边界四要素**（按 `limit`，闭区间 `[1, 100]`）—— **内点** `50` · **外点** `0` · **两端点** `1` 与 `100` · **两端外各一单位** `-1` 与 `101`（拒绝）；**可分辨性** = 确定性等式；**索引** = 契约 §二 要求 `orders(user_id, created_at DESC)` 索引存在（结构性判据，仅作 `AC-09` 的支撑，**不单独承载性能结论**）
- **依据**：`R-04` + `Q-10` + 核对件 `§3.3` 缺口表「订单列表：需后端加分页 / 索引（投产必补）」
- **对应测试用例**：`TC-FEAT-002-09`

### 4.2 账号与会话（`Q-3` / `Q-3` 子项 3-a / `RSK-10`）

### AC-10 注册即开会话｜邮箱口令注册成功即下发会话 cookie 并可直接下单

- **Given** 全新客户端；种子商品按名称定位一件（`stock` ≥ 1）
- **When** ① `POST /api/v1/auth/register`，body `{ "email": <唯一邮箱>, "password": <合规口令> }`；② 用**同一 cookie jar** 加购该商品 `quantity = 1` 并 `POST /api/v1/orders`
- **Then** ① HTTP `201`、`data.user.email` 等于入参邮箱（**大小写归一后**）；响应头 `Set-Cookie` 含会话 cookie 名且带 `HttpOnly`；响应体**不含** `password` / `passwordHash` / 任何哈希字面；② 加购 `201`、下单 `201`、`data.status === "paid"`
- **可验证性要素**：**判定粒度** = 状态码 + 字段存在性 + 字符串等值（不涉时间窗）；**数值口径** = 口令最小长度 **8**（**暂定值，来源 `RSK-10` 缓解建议；已登记 §7 `Q-15`**）；**平台差异** = 一致（HTTP + cookie 由测试显式 jar 维护，不依赖浏览器存储）；**边界四要素**（按口令长度，闭区间 `[8, 128]`）—— **内点** `32` 位随机口令（通过）· **外点** 空串（拒绝）· **两端点** 8 与 128（通过）· **两端外各一单位** 7 与 129（拒绝，`400 INVALID_BODY`）；该档归 `E-02`
- **依据**：`Q-3`（引入最小账号）+ `Q-3` 子项 3-a③ + `RSK-10`
- **对应测试用例**：`TC-FEAT-002-10`

### AC-11 重复注册拒绝｜同一邮箱重复注册返回 409 EMAIL_TAKEN

- **Given** 邮箱 `E` 已注册成功
- **When** 以 `E`（**同形**）与 `E` 的**首字母大写变体**各再注册一次
- **Then** 两次均 HTTP `409` + `code === "EMAIL_TAKEN"`；用户数不增加；`E` 的原会话与订单不受影响
- **可验证性要素**：**判定粒度** = 状态码 + `code` 枚举精确匹配；**数值口径** = 实测值（用户数前后各读一次）；**平台差异** = 一致；**边界四要素** = 不适用（唯一性断言，非阈值）；**大小写说明** = 邮箱按**小写归一**后比较（契约 §四 定死），故大写变体不得绕过唯一约束
- **依据**：`Q-3` + 契约 §四「账号与会话」
- **对应测试用例**：`TC-FEAT-002-11`

### AC-12 登录即开会话｜正确凭据登录成功且会话 cookie 四项属性齐备

- **Given** 已注册账号 `E` / `P`
- **When** `POST /api/v1/auth/login`，body `{ email: E, password: P }`
- **Then** HTTP `200`；`Set-Cookie` 的会话 cookie 同时具备：**`HttpOnly`** · **`SameSite=Lax`** · **`Path=/`** · 非空的 `Max-Age` 或 `Expires`；`data.user.email === E`；随后 `GET /api/v1/auth/me` 返回 `200` 且为同一用户；**重启进程后**同一 cookie 仍可用（`sessions` 落库，见 `AC-01` 的前置设计约束），直到绝对或空闲过期
- **可验证性要素**：**判定粒度** = 属性存在性 + 字符串匹配（`SameSite` 值为枚举精确匹配）；**数值口径** = 会话**绝对有效期 7 天** + **空闲超时 30 分钟**（每次请求滑动续期 `last_seen_at`）= **暂定值，无核对件依据，已登记 §7 `Q-16`**；**平台差异** = **声明一处不一致并给出桌面判据** —— `Secure` 属性在反代终结 TLS 的部署下由配置打开（`COOKIE_SECURE` / `TRUST_PROXY`，见契约 §四），本机 HTTP 下**不得**置 `Secure`（否则真机 cookie 被丢弃、而单测反而看不出来）⇒ 判据只断**前四项**，`Secure` 单独按配置断言（单测覆盖两种配置）；**过期档的可测性** = 用 `createApp({ now })` 的**时钟注入**构造（契约 §八），不真实等待
- **依据**：`Q-3` + `RSK-10`（会话安全）+ 本 PRD `AC-01` 的前置设计约束（会话持久化）
- **对应测试用例**：`TC-FEAT-002-12`

### AC-13 登录失败不辨｜错误口令与不存在邮箱返回同一 401 INVALID_CREDENTIALS

- **Given** 已注册账号 `E` / `P`
- **When** ① 用 `E` + 错误口令；② 用**从未注册**的邮箱 + 任意口令
- **Then** 两次均 HTTP `401` + `code === "INVALID_CREDENTIALS"`，且两次响应的 `code` 与 `message` **完全相同**（不得区分「邮箱不存在」与「口令错误」，防账号枚举）；均不下发会话 cookie
- **可验证性要素**：**判定粒度** = 状态码 + `code` 与 `message` 的**逐字相等**；**数值口径** = 实测值（两次响应体字符串比较）；**平台差异** = 一致；**边界四要素** = 不适用；**可分辨性** = 判据是「两次响应体相等」的确定性等式（1 组即可判定），另以「正确凭据必须 `200`」作**正向对照**（防「一律 401」的假绿）
- **依据**：`Q-3` + `RSK-10`（暴力破解与枚举缓解）
- **对应测试用例**：`TC-FEAT-002-13`

### AC-14 未登录拒下单｜未登录访问下单、订单列表、订单详情均 401 UNAUTHENTICATED

- **Given** 全新会话（无 cookie）且**携带一个可下单的匿名购物车**（`cartId` 有效、含 1 件商品）
- **When** ① `POST /api/v1/orders`；② `GET /api/v1/orders`；③ `GET /api/v1/orders/{任意 orderNo}`
- **Then** 三处均 HTTP `401` + `code === "UNAUTHENTICATED"`；订单数不增加、库存不变、购物车**不清空**（被拒不得产生副作用）
- **可验证性要素**：**判定粒度** = 状态码 + `code` 枚举 + 集合不变（按总纲 §6.4 第 24 条比集合成员与行数）；**数值口径** = 实测值；**平台差异** = 一致；**边界四要素** = 不适用；**与 `409` 的分界** = 「未登录」判**先**：即便购物车为空，未登录也是 `401`（不是 `CART_EMPTY`），该档归 `E-11`
- **依据**：`Q-3` 子项 3-a③（未登录不能下单）+ 核对件 `§5.1.2`

### AC-15 匿名车并入账号车｜登录时匿名车按商品件数相加并入账号车并作废匿名车

- **Given** 匿名会话已加购商品 X `quantity = 2`；账号 A 的车中已有商品 X `quantity = 3`、商品 Y `quantity = 1`
- **When** 在同一 cookie jar 内 `POST /api/v1/auth/login` 成功后 `GET /api/v1/cart`
- **Then** HTTP `200`；车中商品 X **只有一行**且 `quantity === 5`（`2 + 3`，**相加**，不是覆盖）；商品 Y 保留 `quantity === 1`；原匿名 `cartId` 对应的车**不再可寻址**（以旧 `cartId` 请求得到一个**新的空匿名车**，不返回已并入的行）
- **可验证性要素**：**判定粒度** = 按「件」与「行」；**数值口径** = 实测值；**平台差异** = 一致；**边界四要素**（按合并后单行件数，上限沿用 **8** 为**暂定值**，`FEAT-001` 同源）—— **内点** 合并后 5（通过）· **上端点** 合并后恰 8（通过）· **上端点外一单位** 合并后 9 ⇒ `409 QUANTITY_LIMIT_EXCEEDED` 且**合并不发生**（两车均保持原样，无部分写入）· **下端点** 匿名车为空（合并即 no-op）；合并后越限这一档归 `E-19`
- **依据**：`Q-3` 子项 3-a① + 核对件 `§5.1.2`「同商品件数相加，并受既有件数上限（8）约束；合并后匿名 cartId 作废」
- **对应测试用例**：`TC-FEAT-002-15`

### AC-16 退出回到匿名车｜退出登录后回到新的空匿名车，账号车与订单不受影响

- **Given** 账号 A 已登录、登录前已并入一件商品（`AC-15`），且有 1 条订单
- **When** ① `POST /api/v1/auth/logout`；② 同一 cookie jar `GET /api/v1/cart`；③ `GET /api/v1/orders`；④ 重新登录 A 后 `GET /api/v1/cart`
- **Then** ① HTTP `200` 且会话 cookie 被清除（`Max-Age=0` 或等价）；② 返回**新的空匿名车**（`items` 为空、`cartId` 与登录前的匿名 `cartId` 不同）；③ `401 UNAUTHENTICATED`（不得返回 A 的订单）；④ A 的车与订单**与退出前逐项相等**
- **可验证性要素**：**判定粒度** = 按「件 / 单」比集合成员与行数 + cookie 属性；**数值口径** = 实测值；**平台差异** = 一致；**边界四要素** = 不适用；**可分辨性** = 必须同时断言「退出后看不到」与「重登后还在」两面（只断前者会被「退出即清库」的错实现蒙过）
- **依据**：`Q-3` 子项 3-a② + 核对件 `§5.1.2`
- **对应测试用例**：`TC-FEAT-002-16`

### AC-17 我的订单归属｜订单列表与详情只含当前登录用户的订单

- **Given** 账号 A 成功下单 2 次、账号 B 成功下单 1 次（三单 `orderNo` 两两不同）

### AC-18 口令不落日志｜口令明文与口令哈希不出现在日志与响应体

- **Given** 结构化日志输出到可捕获的流（契约 §八 可测性条款提供注入缝）；已执行注册、登录成功、登录失败各 1 次（含一个**特征口令**，如 `Pw-FEAT002-<随机>`）
- **When** 收集整段日志文本与三次响应体文本
- **Then** 三者中**均不含**该特征口令明文；日志中**不含**该用户的 `passwordHash` 字段值、**不含**会话 cookie 值与会话 token；日志行仍含 `request-id` 与该请求的路径
- **可验证性要素**：**判定粒度** = 子串存在性（字符串包含判定，逐条布尔）；**数值口径** = 实测值（特征口令为运行时随机生成，避免与实现里的常量撞车）；**平台差异** = 一致（日志是同进程写入的文本流）；**窗口声明**（总纲 §6.4 第 22 条）= **观测窗口 = 上述三次请求的全时段**（不含启动期与停机期）；**边界四要素** = 不适用

- **对应测试用例**：`TC-FEAT-002-18`

### AC-19 越权返404｜用他人订单号请求详情返回 404 且不暴露资源是否存在

- **Given** 账号 A 有 1 条订单（`orderNo = N_A`）；账号 B 已登录；另有一个**格式合法但从不存在**的订单号 `N_X`
- **When** B 分别 `GET /api/v1/orders/{N_A}` 与 `GET /api/v1/orders/{N_X}`
- **Then** 两次均 HTTP `404` + `code === "NOT_FOUND"`，且**响应体的 `code` 与 `message` 完全相同**（不得出现「无权访问」类文案、不得 `403`）；A 的订单仍可按 `N_A` 查到（正向对照，证明 A 存在且 B 确实被挡）
- **可验证性要素**：**判定粒度** = 状态码 + `code`/`message` **逐字相等**；**数值口径** = 实测值；**平台差异** = 一致；**边界四要素** = 不适用；**可分辨性** = 三次取样构成完整判别（B 查他人 `404` / B 查不存在 `404` / A 查自己 `200`），缺正向对照即可能被「订单详情接口整体 404」蒙过
- **依据**：`Q-3` 子项 3-a④ + 核对件 `§5.1.2`「他人资源返回 `404`（不暴露存在性）而非 `403`；仅『未登录』用 `401`」+ `RSK-11`
- **对应测试用例**：`TC-FEAT-002-19`

### 4.3 错误词表与安全最小集（`Q-9` / `RSK-06`）

### AC-20 错误词表完备｜新码就位且所有错误响应体形态统一无堆栈

- **Given** 服务已启动（含账号面）
- **When** 分别触发 `400`（非法分页、非法体）· `401`（未登录、凭据错）· `404`（商品不存在、他人订单）· `409`（空车、库存不足、邮箱占用）· `413`（体超限）· `429`（限流）· `500`（内部故障）
- **Then** 每一类的响应体**顶层**同时含 `code`（大写下划线字符串，取自契约 §六 的**封闭词表**）与 `message`（非空字符串），**均不含** `stack` / `errno` / 绝对文件路径 / 内部对象；同一 HTTP 码下不同 `code` **互不相同**；全部 `code` 落在词表内（**无词表外码**）
- **可验证性要素**：**判定粒度** = 字段存在性 + 枚举值精确匹配（逐档 1 次请求）；**数值口径** = 实测值（逐档响应体形态）；**平台差异** = 一致；**边界四要素** = 不适用；**词表封闭性** = 断言「响应 `code` 集合 ⊆ 契约词表集合」，实现新增未登记码即判红
- **依据**：`Q-9` + `R-04` + `FEAT-001 AC-29`（存量口径保留，但词表由 8 码扩为 15 码）
- **对应测试用例**：`TC-FEAT-002-20`

### AC-21 内部错误不伪装｜未预期异常一律映射 500 INTERNAL_ERROR，禁止再伪装 404

- **Given** 一个**注入了故障**的实例（测试用独立库/注入缝制造确定性故障，如只读库或强制抛错的语句封装）
- **When** 在该实例上发起一次会踩到内部故障的请求（如 `GET /api/v1/orders` 未登录态以外的受保护请求）
- **Then** HTTP `500` + `code === "INTERNAL_ERROR"`（**不得** `404` / `NOT_FOUND`）；响应体形态仍为 `{code, message}` 且**不含堆栈**；结构化日志中**存在一条** `error` 级记录，且带**与该请求可关联的 `request-id`**；进程**不退出**（单次请求故障不拖垮服务）
- **可验证性要素**：**判定粒度** = 状态码 + `code` 枚举 + 日志字段存在性；**数值口径** = 实测值；**平台差异** = 一致（故障由注入缝确定性制造，不依赖真实磁盘故障）；**边界四要素** = 不适用；**可分辨性** = 断言必须同时覆盖「`500 ≠ 404`」与「日志有对应 `request-id`」，否则「把异常吞掉只回 500」的实现也能过；**客户端中断**（连接提前断开）**不属本条** —— 该情形无法写回响应，只记 `warn` 与计数（契约 §七 裁定），归 `E-20`
- **依据**：`R-04`（投产可观测）+ `Q-9` + 核对件 `§7 RSK-06`；**本条结掉 FEAT-001 的一条未决偏离**（未预期异常被 `safeDispatch` 映射成 `404 NOT_FOUND`），见 §1.5 `S-14`
- **对应测试用例**：`TC-FEAT-002-21`

### AC-22 请求体大小上限｜请求体超过上限返回 413 PAYLOAD_TOO_LARGE

- **Given** 服务已启动
- **When** 对 `POST /api/v1/cart/items`（带 `Content-Type: application/json`）分别发送：体大小恰为上限、上限 **+1 字节**（用 `quantity` 之外的填充字段把体撑大）
- **Then** 恰为上限 → 按业务口径处理（`201` 或 `400`，**不得** `413`）；上限 +1 字节 → `413` + `code === "PAYLOAD_TOO_LARGE"`；服务进程**不崩**、后续正常请求仍 `200`
- **可验证性要素**：**判定粒度** = **字节级**（请求体字节数，按 UTF-8 编码后的字节数）；**数值口径** = 上限 **128 KiB** = **暂定值（依据 `Q-10` 最小可用假设 + `Q-9` 补安全最小集；已登记 §7 `Q-17`）**；**平台差异** = 一致（`Content-Length` 与本机字节计数同源）；**边界四要素** = **内点** 64 KiB（通过）· **外点** 上限 +1 字节（拒绝）· **两端点** 1 字节与 128 KiB（前者由业务校验拒绝、后者按业务处理，均**不得** `413`）· **两端外各一单位** 128 KiB +1 字节（`413`）与 0 字节（`400 INVALID_BODY`，不得 `413`）；**可分辨性** = 逐字节离散计数，1 字节差异即可判定
- **依据**：`Q-9` ① + 核对件 `§2.1` 展开③ `P-09`（现状 `Buffer.concat` 无上限）
- **对应测试用例**：`TC-FEAT-002-22`

### AC-23 写接口三维频次限流｜写接口与登录注册按「每会话 / 每 IP / 全局」三维计数 + 在途并发上限，超限返回 429 RATE_LIMITED

- **Given** 服务已启动；三个维度的窗口阈值分别记为 `R`（**每会话**每窗口）· `R_ip`（**每 IP** 每窗口）· `R_all`（**全局**每窗口），在途并发上限记为 `C`（`AC-63` / `AC-64` 之外的三维计数口径见契约 §一/§七）
- **When** ① 在**同一窗口**内**同一会话**连发 `R` 次与 `R + 1` 次写请求（对 `POST /api/v1/cart/items`；另对 `POST /api/v1/auth/login` 单独一组）；② 同一窗口内用**多个不同会话**、**同一来源 IP**，合计发到 `R_ip + 1` 次；③ 同一窗口内用**多个不同来源 IP**（`TRUST_PROXY=1` 时以 `X-Forwarded-For` 首个 IP 构造），合计发到 `R_all + 1` 次；④ 并发发起 `C + 1` 个写请求（慢速客户端占住连接）
- **Then** ① 前 `R` 次按业务口径应答（不出现 `429`）、第 `R + 1` 次 → `429` + `code === "RATE_LIMITED"`（响应头含 `Retry-After`）；② 该来源 IP 的后续请求 `429`、**其它来源 IP 不受影响**；③ 三维中任一维超限均 `429`（`code` 与 `Retry-After` 同上），且**全局维度不得因单个会话/IP 的额度而失效**；④ 达到在途并发上限时新请求 → `429 RATE_LIMITED`（**复用既有词表码，不新增错误码**）且**不得**进入业务逻辑；窗口结束后（`E-08`）各维均恢复按业务口径应答；**被限流的请求一律不产生副作用**（购物车与订单不变）
- **可验证性要素**：**判定粒度** = **秒级**（窗口为 **60 秒固定窗口**；判定点为「第 `R + 1` 次请求是否落在同一窗口内」）+ 各维计数（整数）；**数值口径** = `R = 60` 次/分钟/**会话**（沿用 `Q-17`）· `R_ip = 4 × R = 240` 次/分钟/**每 IP** · `R_all = 20 × R = 1200` 次/分钟/**全局** · `C = 16`（在途并发上限），窗口 60 秒 = **暂定值（依据 `Q-10` 最小可用假设「并发 ≤50」+ `Q-9` ②；三维阈值与在途并发上限已登记 §7 `Q-23`；**与 `RATE_LIMIT_MAX` 成固定倍数 ⇒ 不新增环境变量**）**；**平台差异** = 一致（服务端时钟判定，测试用同一进程；**来源 IP** 在 `TRUST_PROXY=1` 时取 `X-Forwarded-For` 首个 IP、默认 `0` 时取对端地址 —— 见 `AC-64`）；**边界四要素** = **逐维各给**：**内点** `R - 1` / `R_ip - 1` / `R_all - 1` 次（通过）· **外点** 各 `+ 1` 次（拒绝）· **两端点** `1` 次与 `R`（通过）· **两端外各一单位** `0` 次（不发请求，无意义，以 `1` 为下端点）与各 `+ 1`（拒绝）；**可分辨性** = 差异是 **1 次请求**（离散计数），最小样本量 = 各维 `+ 1` 次；**跨窗口假绿风险** = 连发须在 <1 秒内完成，否则可能跨越窗口边界 ⇒ 用例**重复 3 次**，任一次未观测到 `429` 即判红（总纲 §6.2 第 5 条②：测量步长（1 次请求，毫秒级）远小于判定余量（60 秒窗口））；**维度可分辨性** = 断言必须能区分「是哪个维度拦的」——② 档只允许该 IP 被拦而其它 IP 通过、③ 档只允许全局额度耗尽（否则三维写成同一维即假绿）
- **依据**：`Q-9` ② + 核对件 `§2.1` 展开③ `P-10`（现状无限流）+ `RSK-10`（登录/注册纳入限流，且 `scrypt` 使并发成为资源面）+ **主控 2026-10-16 裁定**（三维 + 在途并发上限；`TRUST_PROXY` 采信真实 IP 见 `AC-64`）
- **对应测试用例**：`TC-FEAT-002-23`

### AC-25 监听端口可配｜`HOST` 与 `PORT` 均可配置，默认仅绑本机

### AC-26 配置校验拒启｜非法配置在启动期非零退出且不进入服务态

- **Given** 逐组非法配置（每次只错一项）：① `PORT` 非整数（`abc`）② `PORT=65536` / `PORT=-1` ③ 会话密钥缺失或过短 ④ `DB_PATH` 指向**不可写**目录 ⑤ 备份保留天数非整数
- **When** 逐组以该配置启动进程
- **Then** 每组均：进程**在监听前退出**，退出码**非 0**；stderr / 日志中**点名出错的那一项变量名**（可读中文或英文说明）；**不产生**监听端口、**不创建**半残服务；`GET /health` 在退出后不可达（无监听）
- **可验证性要素**：**判定粒度** = 退出码（整数） + 日志子串（变量名） + 端口可达性（布尔）；**数值口径** = 实测值（每组各跑一次）；**平台差异** = **声明一处不一致** —— `DB_PATH` 不可写这一档的**错误码**在 macOS 与 Linux 上可能不同（`EACCES` vs `EROFS`）⇒ 判据**只断「非 0 退出 + 日志含 `DB_PATH`」**，不断具体 errno；**边界四要素**（按 `PORT`，闭区间 `[1, 65535]`）—— **内点** `3000`（通过）· **外点** `0`（哨兵，见 `AC-25`，通过）· **两端点** `1` 与 `65535`（通过）· **两端外各一单位** `-1` 与 `65536`（拒绝）；**可分辨性** = 退出码是离散的 0 / 非 0，确定性判定
- **依据**：`R-04` + `P-03`（配置错就启动失败，别带病上线）+ `E-04`
- **对应测试用例**：`TC-FEAT-002-26`

### AC-27 优雅停机与退出｜`SIGTERM`/`SIGINT` 停接新请求、等在途完成、关库后退出 0

- **Given** 服务已启动并已完成一次迁移（库已打开）
- **When** ① 发送 `SIGTERM`（无在途请求）；② 重启后发 `SIGTERM`，同时**已在途**一个下单请求；③ 发 `SIGINT`
- **Then** ① 进程在**有限时间**内退出且退出码 `0`；② 在途下单**正常完成并落库**（重启后仍能查到该单，`AC-01`），随后进程退出 `0`；③ 与 ① 同；三种情形退出前日志各有一条停机记录（含退出原因）
- **可验证性要素**：**判定粒度** = **秒级**（停机耗时上限与「在途请求是否完成」的判定以秒计）；**数值口径** = 停机窗口上限 **10 秒** = **暂定值（依据 `Q-10` 最小可用假设：并发 ≤50，单请求毫秒级 ⇒ 10 秒为宽裕上界；超时后强制退出）**；**平台差异** = 一致（`SIGTERM` / `SIGINT` 在容器与宿主同义；容器 `STOPSIGNAL` 默认即 `SIGTERM`）；**边界四要素** = 不适用（时间窗判据以「在途请求完成 + 退出码 0」承载，不断言精确耗时）；**可分辨性** = 停机上界 10 秒 >> 单请求耗时（毫秒级），测量步长远小于判定余量
- **依据**：`R-04` + `P-04`（现状 `grep -c SIGTERM` = 0）+ `RSK-05`（有库之后强杀会丢/坏数据）
- **对应测试用例**：`TC-FEAT-002-27`

### AC-29 结构化请求日志｜每请求一行 JSON 日志，含 request-id、状态与耗时

### AC-31 静态缓存策略｜带指纹静态资源强缓存、HTML 协商缓存

- **Given** 服务已启动，`web/index.html` 引用的脚本 / 样式与主图带内容指纹查询串（**内容指纹定义钉死：该资源文件「字节」的 `sha256` 前 10 位 hex**，见契约 §7.2）
- **When** ① `GET /`；② `GET /src/**`（**不带**指纹）；③ `GET /src/**?v=<该文件真指纹>`（带**真**指纹）；④ 对 ② 连续请求两次并回带 `If-None-Match`；⑤ **退化指纹档**：`GET /src/**?v=0`、`?v=000000`（长度/形态合法但**不等于**该文件真指纹）
- **Then** ① HTML → `Cache-Control` 含 `no-cache`（或 `max-age=0` + `must-revalidate`）且响应带 `ETag`；② 无指纹静态 → `no-cache` + `ETag`；③ 带**真**指纹静态 → `Cache-Control` 含 `public` 且 `max-age` ≥ `31536000` 且含 `immutable`；④ 第二次返回 `304` 且**响应体为空**；⑤ 退化指纹 → **必须仍返回 `200`** 且按**无指纹档**处置（`no-cache` + `ETag` 协商），**并且不得**返回 `public, max-age=31536000, immutable`（出现该头即**判红**）。**不接受 `404`**（或任何「把已存在的资源说成不存在」的处置）—— **理由（主控 2026-10-16 裁定）**：**资源文件确实存在**，一个伪造查询串**不得**把已存在的资源变成「不存在」；**该档真正要断的是「不得得到 `immutable`」**，不是「可以 `404`」
- **可验证性要素**：**判定粒度** = 响应头字符串匹配（指令存在性 + `max-age` 整数比较）+ 状态码；**数值口径** = 强缓存 `max-age` 上界值 **31536000 秒**为**暂定值（行业常规，非 `Q-10` 推导；本包口径为"≥ 该值"）**；**指纹定义** = `sha256` 前 10 位 hex 为**裁定值**（**主控 2026-10-16 裁定**，目的 = 让「形态合法但退化」的指纹可判红）；**平台差异** = 一致（HTTP 头与 ETag 由本服务生成，不依赖 CDN；指纹由同一 `node:crypto` 计算）；**边界四要素** = 不适用（本条**无阈值型拒绝档**；⑤ 档判的是「**必须返回 `200`** + **不得出现 `immutable` 头**」，**不是**拒绝语义 —— 该档**明确排除 `404`** ⇒ `404` 属**判红**，不是边界档）；**前置依赖** = 「带指纹」由 HTML 渲染期注入（契约 §7.2），若实现不做注入 ⇒ ③ 档**不可构造**，用例须在报告中如实标注该前置是否成立；**⑤ 档不受前置依赖影响**（退化指纹可直接构造）
- **依据**：`R-04` + `P-11`（现状 `grep -c Cache-Control` = 0）+ 核对件 `§2.1` 展开③ + **主控 2026-10-16 裁定**（指纹定义钉死 + 退化档判红）+ **同版收口（主控 2026-10-16）**：⑤ 档**收紧为单一处置**（只允许无指纹档 `no-cache` + `ETag`、**必须 `200`**、**`404` 不接受**；`prdVersion` 仍为 **3**，不另开版本号）
- **对应测试用例**：`TC-FEAT-002-31`

### AC-32 备份保留十四天｜每日备份库文件、保留 14 天、恢复步骤可执行

### AC-37 反代终结TLS｜应用只跑 HTTP，反代示例与说明随部署件交付

- **Given** `deploy/Caddyfile`（**本期反代示例以 Caddy 为准、唯一**；`nginx` 示例**本期不交付**，见 §7 `Q-20`）
- **When** ① 检查应用进程本身是否监听 TLS；② 在容器内做**语法校验**（命令字面见下）；③ 按示例在本机起 Caddy（自签证书）并访问 `https://localhost/health`
- **Then** ① 应用**只监听 HTTP**（无 `https` 监听、无证书文件读取；证书只出现在反代配置里）；② 语法校验退出码 **0**，命令字面 = `docker run --rm -v "$PWD/deploy/Caddyfile:/etc/caddy/Caddyfile:ro" caddy:alpine caddy validate --config /etc/caddy/Caddyfile`；③ 反代转发后 `GET https://localhost/health` 返回 `200` 且响应体与直连一致；④ 文档写明「TLS 由反代终结，应用内不处理证书与续期」（`Q-12`）
- **可验证性要素**：**判定粒度** = 监听类型（布尔：是否存在 TLS 监听）+ 配置校验命令**退出码**（整数）+ HTTP 状态码；**数值口径** = **实测值**（本机可跑；镜像 `caddy:alpine` 与 `nginx:alpine` 均已拉取成功，若某档因网络失败则按**基建假红**分列）；**平台差异** = 一致（反代在容器 / 宿主行为同源）；**边界四要素** = 不适用；**判据落点纪律** = 「配置文件存在」**不单独**承载结论，必须有语法校验或一次真实转发（总纲 §6.4 第 34 条②）
- **为什么选 Caddy 而不选 nginx（实测原因，写死以免 dev 自由发挥）**：nginx 在校验期即解析 `proxy_pass` 的主机名 ⇒ 在 compose 网络**之外**做 `nginx -t` 时，`proxy_pass http://app:3000;` 会因 `host not found in upstream "app"` **退出 1**；要么改用变量上游 `set $up app:3000;` + `proxy_pass http://$up;`，要么在校验命令里带 `--add-host`。Caddy 把上游解析推迟到运行期，`caddy validate` **开箱退出 0**。本包据此**只交付 Caddy**（一条判据、一条命令、一个文件）
- **退出码采集写法（强制，防假绿）**：`<cmd> > "$log" 2>&1; rc=$?` —— **禁止**写成 `cmd | tail` / `cmd | grep` 后再取 `$?`（此时 `$?` 是管道末端命令的退出码，实测过一次把 nginx 的 `1` 读成 `0` 的假绿）。本条与 `AC-36` 的退出码判据**一律适用**；契约 §八 已把该纪律写成可测性条款
- **依据**：`Q-12` + `P-19`（现状无 TLS / 反代）+ 主控一手实测（4 种构造的 `nginx -t` / `caddy validate` 真实退出码）
- **对应测试用例**：`TC-FEAT-002-37`

### AC-48 自托管商品主图（`R-05` / `Q-22`）｜8 张本仓自托管真实主图（JPEG），全部同源且不含任何外部引用

- **Given** 交付仓的 `web/assets/products/`（**本版起为 `P-001.jpg`~`P-008.jpg`**）

- **可验证性要素**：**判定粒度** = 文件个数（整数 8）+ magic bytes（布尔）+ **`SOF` 解析出的边长（整数比较 ≥ 400）** + **宽 == 高（布尔）** + **段长自洽（布尔：逐段 2 字节大端段长均 ≥ 2 且落在文件内）** + **`SOS` 后熵数据非空（布尔）** + **`EOI` 存在且解析一致走到文件尾（布尔）** + `src` 外部引用条数（整数 0）+ `src` 路径正则命中（布尔，逐卡）+ `CREDITS.md` **逐行 6 项齐全（布尔 ×8 —— 判读边界 `R-1`~`R-4`，与 `UI-67` 同口径）** + `CREDITS.md` 内 8 个文件名的出现次数（**整数 ×8**，各 ≥1）；**数值口径** = 8 为**裁定值**（`Q-22`：8 张，对应 8 件种子商品）；**边长下限 400 为裁定值**（**主控 2026-10-16 裁定**；依据 = `UI-12` 的 `aspect-ratio: 1 / 1` + ui-spec §9.1「正方形、短边 ≥ 400px（**下限**）」⇒ `400×400` 合规、更高分辨率**同样合规**）；**本包不保留任何「暂定值」数值阈值**（原 `≥ 2 KiB` 已按同批裁定删除 —— 无依据的字面阈值 = 护栏变噪音）；**平台差异** = 一致（文件系统字节读取与正则匹配同源；**真机观感**「像不像真实商品照」由 UAT 截图交人裁，**不作停点判据**）；**边界四要素** = 不适用；**件数失配档** = 若种子条数变更（`FEAT-001 Q-1` 暂定值可改）⇒ 本条按「主图数 = 种子条数」重判，**不写死 8 与种子解耦**；**与旧版的取代关系（判据语义确有变更）** = 原 `AC-48`「自制 SVG、文本可 diff、含 `<svg>` 根元素、不内嵌位图 base64」**已作废** —— 照片是二进制，**「文本可 diff」这类断言对照片不适用**，由 ② 的 magic bytes + ③ 的 **`SOF` 正方形 / 边长 ≥ 400（下限）** + `AC-49` 的「可取回 + `image/jpeg`」替代；**同版收口（2026-10-16）** = ③ 的原「`≥ 2 KiB` 暂定阈值」**删除**、改为 **`SOF` 解析出正方形且边长 ≥ 400**（主控裁定；test 的 `TC-002-48` 已按此落成，本 PRD 为最后一处旧口径载体）

### AC-49 商品主图可访问（`S-13`）｜`GET /assets/**` 可取到主图且 `content-type` 为 `image/jpeg`

- **Given** 服务已启动；`web/assets/products/` 下已有 8 张 `.jpg` 主图（**现状实测：`/assets/**` 会 404 且套用 API 商品文案**）

### 4.7 真源覆盖缺口补登（`AC-57`~`AC-64`，2026-10-16 主控裁定）

### AC-63 会话密钥真被消费｜换 `SESSION_SECRET` 后旧会话失效（HMAC 派生确实生效）

- **Given** 服务以 `SESSION_SECRET = S1`（长度 ≥ 32）启动并登录成功，取得会话 cookie `C1`（同一库文件）

### AC-64 反代头真被采信｜`TRUST_PROXY=1` 时按 `X-Forwarded-For` 真实 IP 计数，`=0` 时伪造头无效

- **Given** 服务分别以 `TRUST_PROXY=1` 与默认 `0` 启动；IP 维度限流阈值为 `R_ip`（`AC-23`）
- **When** ① `TRUST_PROXY=1`：在**同一窗口**内，用**多个不同 `X-Forwarded-For`** 值（模拟不同来源 IP）交替发送写请求，直到某一个来源 IP 累计到 `R_ip + 1` 次；② 同窗口、同一会话，用同一组伪造 `X-Forwarded-For` 但**不设** `TRUST_PROXY`（默认 `0`）重复一次
- **Then** ① 计数**按 `X-Forwarded-For` 的首个（最左）IP** ⇒ 该来源 IP 的后续请求 `429 RATE_LIMITED`（含 `Retry-After`）、**其它来源 IP 的请求不受影响**（证明转发头被**采信**，不是被忽略）；② `TRUST_PROXY=0` 时**不采信**转发头（一律按对端地址计数）⇒ 伪造 `X-Forwarded-For` **不能**获得额外额度、也**不能**把限流甩给别的 IP
- **可验证性要素**：**判定粒度** = 状态码 + `code`（枚举）+ 按来源 IP 的计数（整数）；**数值口径** = `R_ip = 4 × RATE_LIMIT_MAX = 240` 次/分钟/每 IP = **暂定值（见 §7 `Q-23`；与每会话阈值成固定倍数 ⇒ 不新增环境变量）**；**平台差异** = 一致（服务端取对端地址 / 转发头首值）；**边界四要素** = **内点** `R_ip - 1` 次（通过）· **外点** `R_ip + 1` 次（`429`）· **两端点** `1` 次与 `R_ip` 次（通过）；**假绿封堵（关键）** = 若实现**忽略**转发头，① 档的差异**观测不到**（所有来源都落同一对端地址）⇒ 用例**必须同时跑 ② 档作为对照**，**只跑 ① 不构成证明**；**明示受测对象** = **配置的「生效性」**（此前契约 / 部署件承诺「采信」，而 `AC-23` 只有**每会话**维度 ⇒ 证不了 IP 维度）
- **依据**：契约 §7.1（`TRUST_PROXY` 说明 = 「是否信任反代传来的 `X-Forwarded-*`（**限流取真实 IP 用**）」）· `deploy/Caddyfile`（透传 `X-Forwarded-*`，`TRUST_PROXY=1` 时才采信）· `docs/DEPLOY.md` 变量表（「置 `1` 时采信反代透传的转发头」）· `AC-23`（三维限流，本条的 IP 维度）· **主控 2026-10-16 裁定**（B 档补洞 #2）
- **对应测试用例**：`TC-FEAT-002-64`
