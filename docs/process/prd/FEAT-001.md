## 4. 验收标准（`AC-N`，Given / When / Then）

> **标题格式（强制）**：`### AC-N <中文短名（6–12 字）>｜<一句话结论>`。短名取材于结论句主干、**一处定死**，下游（台账 / 契约 / uat 清单 / 测试 / 报告 / 证据文件名）一律照抄，禁止另起别名。
> 每条 AC 必须**可自动化断言**：给出**具体期望值**（状态码、`code` 字段值、字段名、类型、数量、顺序、文案关键字）。
> **判据不得依赖夹具主键**：全部用「商品名称 + 可观察行为」定位（如「按名称找到《手冲咖啡壶》这件商品」），禁止把 `P-001` 这类主键写进判据正文或步骤。
> **对应测试用例**列由测试角色回填，命名形如 `TC-FEAT-001-01`。

### 4.1 商品列表

### AC-01 列表展示八件商品｜按名称找到种子商品时，列表恰好展示 8 件且每件都有名称与整数分价格

- **Given** 服务已启动，内置只读种子商品（暂定 8 条，见 §7 `Q-1` 与 §9）
- **When** `GET /api/v1/products`
- **Then** HTTP `200`；响应体 `data` 为数组，**元素个数恰好等于 8**；按名称定位任意一件（如逐元素取 `name` 字段做等值比较）均可命中，每件 `name` 为非空字符串、`priceCents` 为**正整数**（`Number.isInteger(priceCents) === true && priceCents > 0`）
- **可验证性要素**：**判定粒度 = 按「件」**（计数单位为 1 件商品，不涉及时间）。**数量口径 = 暂定值 8**（核对件 §3.4 主控暂定，可一句话改）。**边界四要素不在本条**，见 `E-01`（7 件 / 8 件 / 9 件）。**平台差异**：断言只依赖 HTTP JSON 与整数，桌面 / 单测与真机一致，无不一致面（金额换算见 `AC-24`）
- **对应测试用例**：`TC-FEAT-001-01`

### AC-02 列表字段齐全｜列表每件商品的名称、价格分、库存、描述字段均可读且描述非空

- **Given** 同 `AC-01`
- **When** `GET /api/v1/products`
- **Then** HTTP `200`；`data` 每个元素同时含 `id`、`name`、`description`、`priceCents`、`stock` 五个字段且均非 `undefined`；`description` 为**非空字符串**；`stock` 为**正整数**
- **可验证性要素**：判定粒度 = 按「件」；数值口径 = 暂定值（结构断言不依赖具体数值大小）。平台差异：无（纯 JSON 字段存在性与类型）
- **对应测试用例**：`TC-FEAT-001-02`

### AC-03 列表名称有序｜列表按内置种子顺序返回，同一请求重复两次顺序完全一致

- **Given** 服务已启动且无并发写
- **When** 连续两次 `GET /api/v1/products`
- **Then** 两次响应的 `data` 数组中 `name` 序列**逐位相等**（同一顺序），且与内置种子给定顺序一致
- **可验证性要素**：判定粒度 = 按「件」逐位比较；数值口径 = 暂定值（顺序由种子给定）。平台差异：无（数组顺序是 JSON 语义的一部分）
- **对应测试用例**：`TC-FEAT-001-03`

### AC-04 列表只读不可改｜列表接口不提供增删改通道，商品数据在多次请求间保持不变

- **Given** 同 `AC-03`
- **When** 连续两次 `GET /api/v1/products`（中间不发任何写请求）
- **Then** 两次响应的 `name` / `priceCents` / `stock` **逐元素完全相等**；且对 `/api/v1/products` 发 `POST` / `PUT` / `DELETE` **均不产生商品变更**（`AC-03` 的第三次读取仍与前两次相等）
- **可验证性要素**：判定粒度 = 按「件」比集合成员与取值（对总纲 §6.4 第 24 条「幂等断言必须比集合」）；数值口径 = 暂定值。平台差异：无
- **对应测试用例**：`TC-FEAT-001-04`

### AC-05 库存字段可见｜列表与详情都返回库存字段，且同一商品的库存两处取值相等

- **Given** 同 `AC-01`
- **When** `GET /api/v1/products` 取某商品 `stock`，再按**商品名称**定位后 `GET /api/v1/products/{该商品 id}`
- **Then** 两处 `stock` 均为正整数且**取值相等**
- **可验证性要素**：判定粒度 = 按「件」；数值口径 = 暂定值。**定位方式**：先用名称在列表里解析出 `id`，再拼详情路径 —— 脚本按名称解析，**不得写死主键**（总纲 §6.4 第 28 条）
- **对应测试用例**：`TC-FEAT-001-05`

### 4.2 商品详情

### AC-06 详情与列表一致｜按名称进入详情后，名称、价格分、库存与列表同商品逐项相等

- **Given** 同 `AC-01`；已按名称从列表中解析出目标商品 `id`
- **When** `GET /api/v1/products/{id}`
- **Then** HTTP `200`；`data.name`、`data.priceCents`、`data.stock` 与该商品在列表中的同名项**逐项相等**
- **可验证性要素**：判定粒度 = 按「件」逐字段；数值口径 = 暂定值。平台差异：无
- **对应测试用例**：`TC-FEAT-001-06`

### AC-07 详情价与总额相符｜详情价格分乘以件数等于购物车行小计分，无浮点尾差

- **Given** 按名称定位任一商品，其 `priceCents` 记为 `P`；购物车中该商品件数为 `Q`
- **When** 依次 `POST /api/v1/cart/items`（该商品、`quantity = Q`）与 `GET /api/v1/cart`
- **Then** 该行 `lineTotalCents` **严格等于** `P × Q`（用 `===` 比较整数，**不允许**做 `Math.round` 后再比较）；`lineTotalCents` 为整数
- **可验证性要素**：判定粒度 = **金额按「分」**（整数，无小数）、**数量按「件」**；数值口径 = 暂定值（`P` / `Q` 由种子与用例给定）；**可分辨性**：本判据是**确定性等式**（无门限、无统计量），故不适用总纲 §6.2 第 5 条的最小样本量要求 —— 一次比较即可判真伪。平台差异：桌面 / 单测与真机一致（整数算术，不依赖浮点序列化）
- **对应测试用例**：`TC-FEAT-001-07`

### 4.3 购物车（增 / 改 / 删 / 查）

### AC-08 首访下发购物车｜未登录首次访问即返回空购物车并下发匿名 cartId cookie

- **Given** 全新 HTTP 客户端（无任何 cookie），服务已启动
- **When** `GET /api/v1/cart`
- **Then** HTTP `200`；响应头 `Set-Cookie` 含 `cartId=` 且带 `HttpOnly`；响应体 `data.items` 为**空数组**、`data.totalCents === 0`
- **可验证性要素**：判定粒度 = 按「件」（空数组长度 0）。**鉴权口径**：本包无鉴权（`N-1`）⇒ 断言中**不得**出现 `Authorization` 头。平台差异：cookie 由 HTTP 层处理，桌面 / 单测与真机一致（测试用显式 cookie jar，不依赖浏览器的自动存储）
- **对应测试用例**：`TC-FEAT-001-08`

### AC-09 购物车结构完整｜购物车返回行、件数、行小计与总额四类字段且类型正确

- **Given** 已通过 `AC-11` 加入至少一行商品
- **When** `GET /api/v1/cart`
- **Then** HTTP `200`；`data.items` 每行含 `productName`、`unitPriceCents`、`quantity`、`lineTotalCents`；`data.quantityTotal` 等于各行 `quantity` 之和；`data.totalCents` 等于各行 `lineTotalCents` 之和；三者均为整数
- **可验证性要素**：判定粒度 = 数量按「件」、金额按「分」；数值口径 = 暂定值。平台差异：无
- **对应测试用例**：`TC-FEAT-001-09`

### AC-10 加购单件成功｜按名称加入某商品 1 件后，该行出现且件数为 1

- **Given** 全新购物车（`AC-08` 后）
- **When** `POST /api/v1/cart/items`，按名称定位的商品 + `quantity = 1`
- **Then** HTTP `201`；再次 `GET /api/v1/cart` 时**按 `productName` 可定位到该行**，`quantity === 1`、`lineTotalCents === unitPriceCents`
- **可验证性要素**：判定粒度 = 按「件」；数值口径 = 暂定值。**量程内点 = 1 件**（量程下端点，见 `AC-13` 边界四要素）。平台差异：无
- **对应测试用例**：`TC-FEAT-001-10`

### AC-11 重复加购累加｜同一商品重复加入时合并为一行，件数为各次之和

- **Given** 同 `AC-10`
- **When** 对**同一商品**连续两次 `POST /api/v1/cart/items`，`quantity` 分别为 2 与 1（合计 3，在量程 1~8 内）
- **Then** 两次均 HTTP `201`；`GET /api/v1/cart` 中该商品**只占一行**（`items` 长度 1）、`quantity === 3`、`lineTotalCents === unitPriceCents × 3`
- **可验证性要素**：判定粒度 = 按「件」；数值口径 = 暂定值。**内点 = 3 件**（量程 1~8 内）。平台差异：无
- **对应测试用例**：`TC-FEAT-001-11`

### AC-12 非整数件数拒绝｜件数不是整数时拒绝加购，购物车保持原状

- **Given** 购物车已有一行（按名称定位的商品、件数 1），记 `totalCents` 为 `T`
- **When** `POST /api/v1/cart/items`，`quantity` 分别取 `1.5` 与 `"2"`（字符串数字，非整数类型）
- **Then** 两次均 HTTP `400`、`code === "INVALID_QUANTITY"`；随后 `GET /api/v1/cart` 的 `totalCents` 仍**等于 `T`**、行数与件数均未变
- **可验证性要素**：判定粒度 = 按「件」（整数量程）；数值口径 = 暂定值；判据是**类型 + 原子性**双重断言，不依赖浮点比较。平台差异：**声明为一致** —— 但须注意 `1.5` 经 JSON 往返后仍是 number，字符串 `"2"` 在宽松实现下可能被隐式转换 ⇒ 用例必须**同时覆盖两种形态**，只测其一不足以证明类型校验存在
- **对应测试用例**：`TC-FEAT-001-12`

### AC-13 件数上下限拒绝｜件数 0 或负数、9 及以上均拒绝，1 与 8 通过

- **Given** 全新购物车
- **When** 对**每次尝试各用一件不同商品**（`quantity = 8` / `1` / `0` / `-1` / `9` 各打一件**不同**商品，**不是**打同一件累加 —— 以此隔离「件数量程」与「同一行累加」两个因子），依次调 `POST /api/v1/cart/items`
- **Then** **`8` 与 `1` → HTTP `201`**（两端各一点，闭区间 `[1, 8]`）；**`0`、`-1`、`9` → HTTP `400` + `code === "INVALID_QUANTITY"`**（两端外各一单位）；因每次打的是**不同**商品，各行互不累加（「同一件商品累加致越限」的 `409 QUANTITY_LIMIT_EXCEEDED` 归 `AC-14`，**不在本条**）；被拒请求**不改变**购物车
- **可验证性要素**：**边界四要素齐备** —— 内一点 `5`（可另测，应通过）、外一点 `0`、两端各一点 `1` 与 `8`、两端外各一单位 `-1` 与 `9`（应拒绝）。**判定粒度 = 按「件」（整数）**，量程 `[1, 8]` 为**闭区间**。**数值口径 = 暂定值**（单行件数上限 8 = 核对件 §3.4「单次购物车行数上限」同源暂定值，可一句话改）。**平台差异**：整数比较，桌面 / 单测与真机一致
- **对应测试用例**：`TC-FEAT-001-13`

### AC-14 单品上限拒绝｜单行件数上限为 8，第 9 件使该行拒绝且原行保持 8

- **Given** 某商品已在购物车中 `quantity = 8`（`AC-13` 的上端点）
- **When** 再对同一商品 `POST /api/v1/cart/items`，`quantity = 1`（合计将达 9）
- **Then** HTTP `409`、`code === "QUANTITY_LIMIT_EXCEEDED"`；`GET /api/v1/cart` 该行 `quantity` **仍为 8**（未部分写入）
- **可验证性要素**：边界四要素 = 内点 8 件通过（`AC-13`）、外点 9 件拒绝（本条）、端点 8（`AC-13`）、端点外 9（本条）。判定粒度 = 按「件」；数值口径 = 暂定值 8。**409 语义**：该操作对**任何**购物车主体都不允许（与主体身份无关）⇒ 按总纲 §6.4 第 16 条用 `409` 而非 `403`。平台差异：无
- **对应测试用例**：`TC-FEAT-001-14`

### AC-15 加购无货拒绝｜库存为 0 的商品拒绝加购，且不改动购物车

- **Given** 存在一件 `stock === 0` 的商品（由测试注入的独立种子构造，见契约「可测性条款」）；购物车为空
- **When** `POST /api/v1/cart/items`，该商品 `quantity = 1`
- **Then** HTTP `409`、`code === "OUT_OF_STOCK"`；`GET /api/v1/cart` 的 `items` 仍为**空数组**、`totalCents === 0`
- **可验证性要素**：**判定对象是「库存」而非件数** ⇒ 边界四要素按库存取值构造：**内点 = `stock >= 1`**（通过，`AC-10`）· **下端点 = `stock === 0`**（本条，拒绝，`409 OUT_OF_STOCK`）· **下端点外（负库存）= 不可达** —— `stock < 0` 的种子在**构造期**就被 `E-14`（种子字段非法）拒绝，**根本进不到运行期**，故本条**不得**以「注入负库存再断言加购被拒」构造（那会形成「既要求拒绝该输入、又要求构造该输入」的自相矛盾）。负库存这一档的判据落在 `E-14`，不放本条。判定粒度 = 按「件」（件数量程见 `AC-13`）；数值口径 = 暂定值。平台差异：无
- **对应测试用例**：`TC-FEAT-001-15`

### AC-16 购物车行数上限｜购物车最多容纳 8 种不同商品，第 9 种拒绝加入

- **Given** 种子里**至少 9 件不同商品**（由测试注入的独立种子构造）；购物车已含 8 种不同商品各 1 件
- **When** 加入第 9 种不同商品（`quantity = 1`）
- **Then** HTTP `409`、`code === "CART_FULL"`；`GET /api/v1/cart` 的 `items` 长度**仍为 8**、`quantityTotal === 8`
- **可验证性要素**：**边界四要素齐备** —— 内一点 `7` 行（通过）、外一点 `9` 行（拒绝，本条）、两端各一点 `8` 行（通过，本条 Given）、两端外各一单位 `9` 行（拒绝）。**判定粒度 = 按「种（行）」**（一行一种商品，单位为 1 行）；**量程 `[0, 8]` 为闭区间**。**数值口径 = 暂定值 8**（= 核对件 §3.4 暂定值，可一句话改；当种子仅 8 条时该上限退化为不可达，故用例必须注入 ≥9 条的独立种子 —— 见 `E-02`）。平台差异：无
- **对应测试用例**：`TC-FEAT-001-16`

### AC-17 购物车改与删｜改件数后行小计与总额同步变化，删除后该商品行消失

- **Given** 购物车按名称含两行商品（件数分别 1 与 2），记 `totalCents` 为 `T0`
- **When** ① `PATCH /api/v1/cart/items/{id}` 把第一行改为 `quantity = 3`；② `DELETE /api/v1/cart/items/{id}` 删除第二行
- **Then** ① HTTP `200`：第一行 `quantity === 3`、`lineTotalCents === unitPriceCents × 3`，`totalCents > T0`；② HTTP `200`：`items` 长度由 2 变 **1**、**按 `productName` 定位不到被删商品**，`totalCents` 等于剩余行的 `lineTotalCents`
- **可验证性要素**：判定粒度 = 数量按「件」、金额按「分」；数值口径 = 暂定值；删除断言用「按名称定位不到」而非「主键不存在」，且**比集合成员与行数**（总纲 §6.4 第 24 条）。平台差异：无
- **对应测试用例**：`TC-FEAT-001-17`

### AC-18 下单即支付成功｜下单后订单状态为已支付并返回唯一订单号

- **Given** 购物车按 `AC-10` 含 1 件商品

### AC-19 下单扣减库存｜下单成功后该商品库存减去购买件数，差值精确相等

- **Then** `stock === S - Q`（整数精确相等）
- **可验证性要素**：判定粒度 = 按「件」；数值口径 = 暂定值。平台差异：无

### AC-20 缺货下单拒绝｜购买件数超过可售库存时拒绝下单，库存与订单均不变

- **Given** 商品库存 `S`；购物车中该商品件数 `Q`（允许加购阶段放行，使 `Q > S` 成立）；下单前订单列表条数记为 `M`、库存记为 `S`
- **When** `POST /api/v1/orders`
- **Then** HTTP `409`、`code === "INSUFFICIENT_STOCK"`；`GET /api/v1/products/{id}` 的 `stock` **仍为 `S`**；`GET /api/v1/orders` 条数**仍为 `M`**（无部分写入、无订单残留）
- **可验证性要素**：**边界四要素齐备** —— 内一点 `Q = S - 1`（通过）、外一点 `Q = S + 1`（拒绝）、两端各一点 `Q = S`（通过，恰好买完）与 `Q = S` 的下端点 `Q = 0`（不可达：件数下限 1，见 `AC-13`，故下端点以 `Q = 1` 当且仅当 `S >= 1` 作为闭区间下端点）、两端外各一单位 `Q = S + 1`（拒绝）。判定粒度 = **按「件」**；数值口径 = **暂定值**（`S` 由种子给定，见 §7 `Q-1`）。**平台差异**：无
- **对应测试用例**：`TC-FEAT-001-20`

### AC-21 总额分为单位｜订单总额等于各行单价分乘件数之和，全程整数无浮点尾差

- **Given** 购物车含 ≥2 行不同商品，件数分别为 `Q1`、`Q2`，单价分分别为 `P1`、`P2`
- **When** `POST /api/v1/orders`
- **Then** `data.totalCents === P1 × Q1 + P2 × Q2`（整数精确相等，**不得**先转元再做浮点乘除）；`data.items` 每行 `lineTotalCents === unitPriceCents × quantity`；订单 `data.totalCents` 与下单前 `GET /api/v1/cart` 的 `totalCents` **相等**
- **可验证性要素**：判定粒度 = 金额按「分」（整数）；数值口径 = 暂定值。**平台差异声明**：断言只走整数算术与 JSON number（安全整数范围内），桌面 / 单测与真机一致；**元换算只在展示层**（`AC-24`），订单接口**不得**返回元为单位的金额字段
- **对应测试用例**：`TC-FEAT-001-21`

### AC-22 空车下单拒绝｜购物车为空时拒绝下单并提示购物车为空

- **Given** 全新购物车（`AC-08` 后，`items` 为空）
- **When** `POST /api/v1/orders`
- **Then** HTTP `409`、`code === "CART_EMPTY"`、`message` 含中文提示「购物车是空的」关键字；`GET /api/v1/orders` 条数不变（为 0）
- **可验证性要素**：判定粒度 = 按「件」（空集合）；数值口径 = 暂定值。**文案关键字**只断言包含关系，最终定稿由 UI 规格承担（本 PRD 不锁整句）。平台差异：无
- **对应测试用例**：`TC-FEAT-001-22`

### AC-23 下单后清空车｜下单成功后购物车被清空，再次下单被拒

### 4.6 种子与金额展示

### AC-28 种子商品可读｜内置 8 条只读种子商品全部满足名称非空、价格分为正整数、库存为正整数

- **Given** 服务以默认种子启动
- **When** 逐件读取 `GET /api/v1/products`
- **Then** 8 条**逐条**满足：`name.trim() !== ""`、`Number.isInteger(priceCents) && priceCents > 0`、`Number.isInteger(stock) && stock > 0`
- **可验证性要素**：判定粒度 = 按「件」+ 金额按「分」；数值口径 = **暂定值**（8 为核对件 §3.4 主控暂定值，可一句话改）。**边界四要素**见 `E-01`（默认种子恰 8 条的正面断言；注入路径接受 0 / 7 / 8 / 9 / 10 任意条数）与 `E-14`（字段非法才拒绝）。平台差异：无。**定位方式**：逐条断言，不引用任何主键
- **对应测试用例**：`TC-FEAT-001-28`

### AC-29 统一错误响应｜所有 4xx 错误响应体形态统一，均含 code 与 message 且无堆栈

- **Given** 服务已启动
- **When** 分别触发 `404`（不存在的商品 id）、`400`（非法件数）、`409`（空车下单）三类错误
- **Then** 三类响应体**形态一致**：顶层含 `code`（大写下划线字符串）与 `message`（非空字符串）两个字段；`code` 取值**互不相同**（分别 `NOT_FOUND`、`INVALID_QUANTITY`、`CART_EMPTY`）；三类响应体**均不含** `stack` / `errno` / 文件路径等内部细节字段
- **可验证性要素**：判定粒度 = 字段存在性 + 枚举值精确匹配；数值口径 = 暂定值（`code` 词表由契约定死）。**平台差异**：无。**无鉴权 ⇒ 无 403 面**（见契约）；本条**不**断言 403
- **对应测试用例**：`TC-FEAT-001-29`

### AC-30 刷新即重置｜购物车与订单不被持久化，新客户端看不到他人购物车与订单

- **Given** 客户端 A 已加购并下单；客户端 B 为全新 cookie
- **When** ① B `GET /api/v1/cart` 与 `GET /api/v1/orders`；② 以同一份种子重建应用实例（模拟进程重启）后，A 再 `GET /api/v1/cart` 与 `GET /api/v1/orders`
- **Then** ① B 的 `items` 为**空数组**、订单为**空数组**（A 的数据不外泄）；② 重建后 A 的 `items` 为空、订单为空、商品库存**回到种子初值**（**② 已被 `FEAT-002` 取代**，新口径「**重启后数据仍在**」，见本条末取代标注）
- **可验证性要素**：判定粒度 = 按「件」比集合成员与行数（总纲 §6.4 第 24 条：`items` 成员与长度的前后差异必须为空）；数值口径 = 暂定值。**平台差异声明**：本条**不得**以「重启进程」为唯一手段（测试环境与真机重启语义不同）⇒ 判据落在**应用工厂：注入独立存储 + 重建实例**上（契约「可测性条款」给出的 `createApp` 入口），使桌面环境可复现

### AC 可验证性要素（缺一即判 AC 不合格，测试有权拒收）

1. **边界四要素**（凡涉及阈值 / 时间窗 / 数量上限）：内一点（应通过）、外一点（应拒绝）、两端各一点（闭区间）、两端外各一秒 / 一单位（应拒绝）。
2. **判定粒度显式**：写清「分钟级 / 秒级 / 毫秒级」，禁止只写"含端点"。
3. **平台差异声明**：凡依赖运行时行为（JSON 库、文件系统、时区、编码、原生 API、内存模型）的 AC，必须写明「桌面 / 单测 与 真机 行为是否一致」；不一致的必须给出能在桌面环境抓住它的判据。
4. **数值口径**：涉及估算 / 换算的，写明是「实测值」还是「估算兜底值」。
5. **阈值类判据自带可分辨性**：凡**门限 + 统计量**（中位数 / 比例 / 分位）的 AC，必须至少写明其一 —— ① 最小样本量 / 最小重复次数；② 「测量步长 < 判定余量」的证明；③ 两者都给不出 ⇒ 不得作为停点判据，只能当观察项。

> **本包自查**：全部 AC 的判定粒度均为**按「件」/ 按「种（行）」/ 按「分」的整数计数**，**无任何时间窗阈值 AC** ⇒ 边界四要素只在「件数 / 行数 / 库存」三处出现，已分别落在 `AC-13`、`AC-14`、`AC-16`、`AC-20`、`E-02`。唯一涉及统计量的判据是 `AC-25` 的「同毫秒 20 次取样」，已写明最小样本量 20。**本包无 AC 依赖墙钟时间**，故不适用「秒级 / 分钟级」粒度声明。
>
> **种子条数为何不再是拒绝边界（`E-01` 的口径，r2 修正）**：**种子条数不是阈值类判据** —— 核对件 §3.4 只把「8 条」定为**暂定值**，`R-01`~`R-09` 与 `Q-1`~`Q-7` 均**未要求**对条数偏离做启动期拒绝，故不存在「内点 / 外点 / 两端外一单位应拒绝」的构造空间。若强行要求拒绝，会与 `AC-16` / `E-02` 冲突：同一个 `createApp({ seed })` 入口被要求**既接受 9 条**（压行数上限外点）**又对 9 条抛错** ⇒ `AC-16` 外点不可能被测出，红灯还会被误归因为产品缺口。r2 因此把「条数偏离即拒绝启动」**整条删除**（删的是本 PRD 自造的要求，不是人的裁定），改用**正面断言**：默认种子恰 8 条 + 注入路径接受任意条数；负分支改由 `E-14`（**字段**合法性）承担 —— 它与任何构造需求都不冲突。比对表见 §11 变更记录 r2 行。
